# 活动、排组与发布

## 1. 创建答辩活动

进入“答辩活动”，填写：

- 院系；
- 活动名称；
- 学年；
- 学期；
- 可选的学期资料。

活动创建后，继续配置规则、时段和教室。缺少其中任何一项时，排组前检查会说明缺失内容。

## 2. 配置规则

| 规则 | 含义 |
| --- | --- |
| 每组学生数 | 一个答辩组允许安排的学生上限 |
| 每组教师数 | 每个答辩组必须安排的教师数量 |
| 组长最低职称等级 | 组长教师必须达到的等级 |
| 教师工作量上限 | 一名教师在本活动中最多参加的组数 |

页面还提供五个排序权重。权重只影响多个合格方案之间的选择，不会允许违反必须满足的条件：

- 学生人数均衡：减少各组人数差异；
- 教师工作量均衡：减少教师之间的组数差异；
- 方向匹配：优先让教师方向与学生方向接近；
- 时间集中：减少安排过度分散；
- 例外使用：优先选择不需要例外的安排。

如果不确定权重，先使用默认值。调整权重后应生成新方案并比较，不要直接改变已发布方案。

## 3. 添加时段和教室

每个时段包含日期、开始时间、结束时间和最大组数。同一活动的时段不能互相重叠。

教室需要先存在于院系主数据，再加入活动可用教室。实际可安排组数取决于：

- 时段的最大组数；
- 该时段可用的教室数；
- 教室容量；
- 学生和教师在该时段是否有课程占用或请假。

例如，一个时段允许 4 组，但只有 2 间可用教室，那么这个时段最多安排 2 组。

## 4. 排组前检查

提交任务前，系统先检查明显无法完成的情况，包括：

- 学生数和目标组数不匹配；
- 教师总工作量不足；
- 符合组长职称的教师不足；
- 时段或教室容量不足；
- 某个学生没有任何可用时段；
- 教师回避或其他限制使某组无法组成。

检查失败时先处理提示中的数据，不要反复提交相同任务。提示会尽量给出涉及的对象和条件。

## 5. 提交并查看排组任务

填写随机种子和时间上限后提交。随机种子是一个整数，用于让同一份输入更容易重复得到相同结果。

任务状态：

| 状态 | 含义 |
| --- | --- |
| 等待 | 已记录，等待求解进程开始 |
| 运行中 | 正在生成安排 |
| 成功 | 已保存完整方案 |
| 失败 | 没有得到可保存的方案，页面会显示原因 |
| 已取消 | 在开始前或运行过程中取消 |

重复点击时，客户端会携带同一个请求标识。服务端识别到重复请求后返回原任务，避免生成多个相同任务。

达到时间上限时，如果已经找到完整且合格的方案，系统会保存该方案并说明它不一定是排序分数最好的方案；如果没有完整方案，则返回失败说明。

## 6. 查看和比较方案

方案中每个组都应包含：

- 组号；
- 学生名单；
- 教师名单；
- 组长；
- 时段；
- 教室；
- 排序分数和例外使用情况。

“比较方案”会列出学生移动、教师变化、时段变化、教室变化、分数变化和例外使用变化。比较时先确认两个方案属于同一个活动。

## 7. 手工调整

已准备好的方案可以复制为草稿，再修改组的时段、教室或成员。每次保存会带上页面读取到的版本号。

如果另一个人已经修改，系统返回“版本冲突”，不会覆盖对方的修改。刷新页面，查看最新内容后重新决定。

保存手工调整时，系统检查整个受影响方案。没有已批准例外的导师回避、时间冲突、重复安排、容量不足等问题会阻止保存。

## 8. 检查并发布

发布前执行“检查方案”。系统使用独立检查程序重新检查全部安排，不直接相信排组程序的结果。

通过后可以发布。发布会：

1. 在同一数据库事务中再次检查；
2. 把当前方案标记为已发布；
3. 把该活动此前已发布的方案标记为已归档；
4. 写入审计记录。

如果发布检查失败，方案回到草稿状态，不会留下半发布数据。

已发布方案不能手工修改。确需变更时：

1. 复制已发布方案；
2. 在新草稿中调整；
3. 重新检查；
4. 发布新版本；
5. 导出并通知教师使用新版本。

## 9. 教师确认

发布后，教师在“我的安排”看到自己的答辩任务。确认操作只表示教师已收到安排，不会修改方案。重复确认返回同一结果，不会生成多条有效确认。
