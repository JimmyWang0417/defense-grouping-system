# 常见问题

## 安装和启动

### `uv sync --locked` 提示锁文件不一致

不要删除 `uv.lock`。先确认当前分支完整，再执行：

```bash
git status
git pull --ff-only
uv sync --locked
```

只有在有意修改依赖时才执行 `uv lock`，并把 `pyproject.toml` 与 `uv.lock` 一起评审。

### API 启动后立即退出

依次检查：

1. `DEFENSE_JWT_SECRET` 是否至少 32 字符；
2. 数据库目录是否可写；
3. 是否执行过 `uv run alembic upgrade head`；
4. 8765 端口是否已被其他程序占用；
5. PostgreSQL 地址、用户名、密码和网络是否正确。

### 健康检查失败

```bash
curl -v http://127.0.0.1:8765/api/v1/health
```

连接被拒绝表示 API 没有监听该地址或端口。返回 500 表示进程已收到请求但内部失败，应查看同一时间的服务日志。

## 登录和权限

### 忘记管理员密码

`init-admin` 不会覆盖已有管理员。不要直接修改数据库中的密码摘要。应由另一名系统管理员在用户管理中重置；如果没有其他管理员，按事故恢复流程在停机和备份后处理。

### 页面有菜单，但操作返回 403

服务端会再次检查角色和院系。查看错误代码：

- `forbidden`：角色不允许；
- `department_scope_denied`：对象不在账号授权院系；
- `password_change_required`：需要先修改临时密码。

不要通过共用系统管理员账号绕过院系限制。

### 登录多次失败后提示 429

这是登录限速。按照响应头 `Retry-After` 指示的秒数等待，再确认用户名和密码。不要连续重试。

## Excel 导入

### 提示工作表或表头不正确

重新下载当前版本模板，把数据粘贴到模板的数据行。不要改工作表名称和第一行，不要把旧模板表头手工改成看起来相似的文字。

### 提示导师、专业或方向不存在

先在主数据页面确认这些记录属于同一院系，名称和工号完全一致。补齐主数据后重新上传检查。

### 检查成功但确认导入失败

可能有人在检查后修改了相关主数据，或同一批数据已由别人确认。刷新导入批次和对应列表，重新检查后再确认。系统失败时不会只写入一部分行。

### 重复导入会不会产生重复数据

学生按学号、教师按工号识别已有数据。重复文件通常显示为更新或不变。确认前查看数量；不要假设重复导入一定无变化。

## 排组

### 提示教师总工作量不足

需要的教师工作量约为“组数 × 每组教师数”。检查启用教师数量、每人工作量上限、时间可用性和导师回避。不要只提高上限而不确认教师实际能参加。

### 提示时段或教室容量不足

检查每个时段的最大组数、活动可用教室、教室可用时间和容量。一个时段能安排的组数不会超过同时可用教室数。

### 任务一直显示运行中

先等待页面设置的时间上限。若 API 非正常退出，重启后系统会把中断的运行中任务标记为失败，不会一直保留假运行状态。重新提交前先查看失败原因。

### 相同数据为什么结果不同

确认规则、时段、教室、例外和随机种子是否都相同。任何输入变化都可能改变结果。需要复现时记录方案版本和随机种子。

### 手工调整提示版本冲突

另一个用户已经保存了修改。刷新方案，查看最新版本后重新操作。系统不会覆盖较新的修改。

### 发布失败但自动排组成功

发布会重新读取当前数据并检查完整方案。排组之后新增的请假、课程占用、例外撤销或主数据变化都可能使发布失败。按照发布错误修正，再重新检查。

## 备份和恢复

### SQLite 能否在 API 运行时备份

可以。`uv run defense-grouping backup` 使用 SQLite 在线备份功能创建一致性副本。恢复前必须停止 API。

### 校验清单（manifest）校验失败

不要绕过。文件可能不完整、被修改或与 manifest 不配套。换用另一份已验证备份，并保留失败文件用于检查。

### PostgreSQL 如何恢复

先恢复到隔离数据库，核对结构版本、表数量、登录、权限和已发布方案导出。通过后再安排停机切换。详细步骤见 [备份与恢复](https://github.com/JimmyWang0417/defense-grouping-system/blob/main/docs/operations/backup-recovery.md)。

## GitHub 仓库

### 为什么不能直接推送 main

main 已启用仓库规则。变更必须推到新分支，创建合并申请（Pull Request），并等待名为 `PR Gate` 的总检查成功后合并。

### 自动发布为什么没有创建发布 PR

检查仓库是否存在名为 `RELEASE_PLEASE_TOKEN` 的 Actions secret，并确认它对该仓库有 Contents 与 Pull requests 读写权限。默认 `GITHUB_TOKEN` 创建的 PR 不会自动触发后续工作流，因此这里使用单独的最小权限 token。

### 如何报告问题

请提供：

- 操作步骤；
- 页面错误代码和请求编号；
- 发生时间和所用方案版本；
- 可以脱敏后的输入示例；
- 预期结果和实际结果。

不要附带真实密码、token、JWT secret 或未经脱敏的师生数据。
