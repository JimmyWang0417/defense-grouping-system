# 答辩分组系统设计规格

## 1. 项目目标

构建一套面向学校教务工作的答辩分组系统。系统使用 Flet 提供桌面端与 Web 端界面，使用 FastAPI 提供统一后端 API，首版可在一台个人电脑上完整运行，后续能够迁移到服务器和 PostgreSQL。

系统需要完成从基础数据导入、答辩活动配置、自动排组、冲突解释、人工调整、例外审批、方案发布到 Excel 导出的完整闭环，并确保导师回避、课表冲突、请假特例等实际教务规则得到可靠执行。

## 2. 范围与验收边界

### 2.1 首版范围

- 三级账号权限：系统管理员、教务管理员、教师。
- 固定 Excel 模板导入，同时支持界面增删改查。
- 管理院系、专业、教师、学生、导师关系、专业方向、课程占用、请假记录、教室和标准时段。
- 配置答辩活动、组数、容量、教师人数、组长职称门槛、工作量和方向匹配规则。
- 自动分配学生、答辩教师、组长、日期时段和教室。
- 对导师回避、课表、请假、资源占用等硬约束进行校验。
- 在硬约束无法满足时给出可理解的原因；只有经过审批的具体例外才能放宽对应约束。
- 保存多个方案版本，支持比较、人工调整、复检、发布、撤回和 Excel 导出。
- 保存导入、审批、排组、调整、发布和账号管理等审计记录。
- 本机使用 SQLite，服务器部署时支持切换 PostgreSQL。
- 参考环境为 8 核 CPU、16 GB 内存；500 名学生、50 名教师、20 个答辩组在 60 秒内生成可行方案，求解过程内存峰值不超过 2 GB。

### 2.2 全校级定位

数据模型、API、权限和任务接口按全校级使用设计。首版性能验收以院系级数据为准，每次以一个院系为求解单元；未来可在服务器上通过 PostgreSQL 和任务队列并行处理多个院系。

### 2.3 首版不包含

- 与现有教务系统的专有接口直连。
- 短信、企业微信或邮件通知。
- 学生端账号与在线选组。
- 原生移动端上的复杂排组编辑；移动端只保证查看已发布安排。
- 跨院系联合答辩的全局联合优化。
- 自动生成逐名学生的分钟级答辩顺序。

## 3. 用户与权限

### 3.1 系统管理员

- 维护用户、角色、院系和全局参数。
- 查看系统运行状态、全部审计记录和备份状态。
- 初始化或停用账号，但不能查看用户密码。

### 3.2 教务管理员

- 维护授权院系内的师生、导师关系、课表、请假、教室和答辩活动。
- 导入和导出数据，创建排组任务，调整和发布方案。
- 发起例外申请；具有审批权限的教务管理员不能审批自己提交的申请。
- 只能访问被授权院系的数据。

### 3.3 教师

- 查看与自己相关的已发布答辩安排。
- 确认本人安排，并查看必要的组内成员与地点信息。
- 不能查看草稿方案、其他院系数据或修改排组结果。

## 4. 总体架构

```text
Flet 桌面/Web 客户端
        │ HTTPS / REST
        ▼
FastAPI 后端
├── 身份认证与三级权限
├── 基础数据与 Excel 导入
├── 答辩活动配置
├── 排组任务与方案版本
├── 人工调整与例外审批
├── 结果导出与审计日志
└── OR-Tools CP-SAT 求解器
        │
        ▼
SQLAlchemy 数据访问层
├── 本机：SQLite
└── 服务器：PostgreSQL
```

客户端不直接访问数据库。客户端与后端可以在本机由一个开发启动器同时拉起，也可以分别连接到服务器。所有业务校验都在后端执行，Flet 只负责交互、输入预检提示和结果展示。

首版由 FastAPI 进程内的后台任务执行导入和求解，但通过统一的任务执行接口隔离。服务器版本可将实现替换为 Redis 加 Celery 或 RQ，API 和客户端不随之变化。

## 5. 后端模块边界

### 5.1 `auth`

负责用户、登录、令牌、密码修改、角色和院系数据范围。任何业务模块只通过当前用户上下文获得权限，不自行解析令牌。

### 5.2 `master_data`

负责院系、专业、教师、学生、导师关系、专业方向、课程占用、请假记录、教室和标准时段。对外提供稳定的查询和批量校验接口。

### 5.3 `defense`

负责答辩活动、活动规则、可用时段、可用教室和活动参与范围。活动在生成首个方案后仍可修改，但规则变化会使旧草稿标记为“需要重新校验”。

### 5.4 `scheduling`

负责候选域生成、数据预检、CP-SAT 模型、求解任务、冲突解释、方案版本、质量指标和发布前复检。该模块不负责 HTTP 或界面逻辑。

### 5.5 `approval`

负责例外申请、审批、拒绝、撤销和有效范围。排组模块只能读取已经批准且仍有效的例外。

### 5.6 `imports_exports`

负责模板生成、文件解析、预检报告、确认导入和方案导出。该模块将外部表格映射为业务命令，不绕过业务校验直接写库。

### 5.7 `audit`

负责追加式审计记录。业务模块通过统一接口写入操作者、动作、对象、请求编号以及变更前后摘要。

## 6. 核心数据模型

### 6.1 组织与人员

- `Department`：院系。
- `Major`：专业，隶属一个院系。
- `User`：登录账号、密码摘要、状态和首次登录标志。
- `RoleAssignment`：用户角色与可访问院系。
- `Teacher`：工号、姓名、职称、所属院系、专业方向和工作量上限。
- `Student`：学号、姓名、专业、年级、专业方向和导师。
- `Direction`：可复用的专业方向标签。

### 6.2 可用性与资源

- `CourseOccupancy`：人员、具体日期或重复教学周规则、节次范围。
- `LeaveRecord`：人员、起止时间、原因和状态。
- `DefenseSlot`：活动中的标准时段，包含日期、开始时间和结束时间。
- `Room`：校区、楼宇、教室名称和容量。
- `ActivityRoom`：某答辩活动允许使用的教室。

课程占用和请假在进入求解器前统一转换为“人员在标准时段是否可用”，并保留原始记录用于解释冲突。

### 6.3 答辩与方案

- `DefenseActivity`：名称、院系、学年学期、状态和规则版本。
- `ActivityRuleSet`：组容量、每组教师数、组长职称门槛、工作量上限和软目标权重。
- `ScheduleJob`：任务类型、状态、进度、输入摘要、随机种子、开始结束时间和错误信息。
- `SchedulePlan`：方案版本、来源方案、状态、求解参数、质量指标和创建人。
- `DefenseGroup`：方案内的答辩组、标准时段和教室。
- `PanelAssignment`：答辩组中的教师及其组长身份。
- `StudentAssignment`：答辩组中的学生。
- `TeacherConfirmation`：教师对已发布安排的确认状态。

方案状态为 `draft`、`validating`、`ready`、`published` 或 `archived`。发布后的方案不可原地修改；任何修改都从已发布版本复制出新草稿。

### 6.4 治理与追踪

- `ConstraintException`：例外类型、作用对象、作用时段、原因、申请人、审批人、有效期和状态。
- `ImportBatch`：文件摘要、模板类型、预检结果、确认人和写入统计。
- `AuditLog`：追加式操作记录。
- `RefreshToken`：刷新令牌摘要、设备信息、有效期和撤销状态。

所有主要业务表包含稳定 UUID、创建时间、更新时间和乐观锁版本号。展示用编号与数据库主键分离。

## 7. Excel 导入与导出

系统提供带字段说明和示例行的固定模板包：

- `学生信息.xlsx`：学号、姓名、院系、专业、年级、专业方向、导师工号。
- `教师信息.xlsx`：工号、姓名、院系、职称、专业方向、工作量上限。
- `课程占用.xlsx`：人员编号、人员类型、日期或教学周、星期、开始节次、结束节次。
- `请假记录.xlsx`：人员编号、人员类型、开始时间、结束时间、原因。
- `答辩时段.xlsx`：活动、日期、开始时间、结束时间、最大组数。
- `教室信息.xlsx`：校区、楼宇、教室、容量、可用日期时段。

导入分为两个阶段：

1. 上传并解析，在临时区域生成逐行错误、警告、重复项和预计新增/更新统计。
2. 用户确认后，在单一事务中写入；任何一行写入失败都整体回滚。

系统按业务编号执行幂等更新。相同文件重复导入不会生成重复人员。导出文件包含分组总表、按教师视图、按学生视图、教室时段表、冲突与例外说明、方案元数据。

## 8. 排组约束与优化目标

### 8.1 硬约束

- 每名参与学生必须且只能进入一个答辩组。
- 每个答辩组的教师数量必须符合活动规则，并且恰有一名符合职称门槛的组长。
- 学生导师不得担任该生所在答辩组的成员。
- 教师和学生不得被安排到课程占用或已批准请假覆盖的时段。
- 同一教师、学生或教室不得在同一时段重复安排。
- 每组学生人数不得超过活动规则、时段限制和教室容量中的最小值。
- 教师工作量不得超过硬性上限。
- 只有状态为已批准、作用对象精确且仍在有效期内的例外才能放宽对应约束。

### 8.2 软目标

按活动规则中的权重依次优化：

1. 各组学生人数差异尽量小。
2. 教师工作量尽量均衡。
3. 学生专业方向与教师组专业方向尽量匹配。
4. 教师参与的时段尽量连续，减少零散安排。
5. 即使例外已获批准，也尽量不实际使用例外。

系统保存每个方案的目标分项得分，便于教务人员比较版本。相同输入、规则和随机种子必须得到可复现结果。

### 8.3 求解流程

1. 校验主数据完整性、容量下界、可用组长数量和明显不可行条件。
2. 将课表、请假和审批例外转换为候选人员与候选时段域。
3. 构建 CP-SAT 变量、硬约束和加权目标。
4. 在活动配置的时间上限内求解，持续更新任务进度与当前最佳质量。
5. 将求解结果转换为新的草稿方案，再使用独立校验器完整复检。
6. 若不可行，返回预检原因和求解器可定位的约束集合；不创建伪成功方案。

## 9. 例外审批

例外必须精确到约束类型和作用范围，例如“允许教师 T 在时段 S 参加答辩，即使存在课程占用”或“允许教师 T 评审学生 X”。不支持一键关闭整个活动的导师回避或请假约束。

流程为：教务管理员提交理由和影响范围，另一名具有审批权限的管理员批准或拒绝。批准记录不能被修改，只能撤销并重新申请。方案详情和导出文件必须标识实际使用的例外。

## 10. API 与任务交互

API 按 `/api/v1` 进行版本化，使用统一的成功分页结构和错误结构。主要资源包括：

- `/auth`：登录、刷新、退出、首次修改密码和当前用户。
- `/users`、`/departments`、`/majors`、`/teachers`、`/students`。
- `/occupancies`、`/leaves`、`/rooms`。
- `/activities`、`/slots`、`/rules`。
- `/imports`、`/exports`。
- `/schedule-jobs`、`/plans`、`/groups`。
- `/exceptions`、`/approvals`、`/audit-logs`。

导入和求解接口返回任务编号。客户端轮询任务状态，首版不要求 WebSocket；任务状态包含阶段、百分比、摘要和可恢复错误。创建任务和发布方案等写操作支持幂等键，避免网络重试造成重复执行。

## 11. Flet 客户端

客户端采用左侧导航、顶部当前活动与用户信息、右侧主工作区的桌面布局。表格支持搜索、筛选、分页、批量操作和错误定位。

主要页面：

- 登录与首次修改密码。
- 工作台：数据概览、待审批、近期活动和任务状态。
- 基础数据：组织、教师、学生和导师关系。
- 可用性管理：课程占用、请假记录和冲突日历。
- 数据导入：模板下载、文件上传、预检和确认导入。
- 答辩活动向导：范围、规则、时段、教室和求解参数。
- 自动排组：启动任务、观察进度、查看冲突解释和质量指标。
- 方案管理：版本比较、人工调整、重新校验、发布和撤回。
- 例外审批：申请、批准、拒绝和撤销。
- 教师门户：本人已发布安排及确认操作。
- 审计中心与系统管理。

人工调整通过表单和可筛选候选列表完成，首版不依赖复杂拖拽。每次调整先在后端校验，再写入新版本；冲突在保存前明确说明。所有破坏性操作二次确认，未保存编辑、网络断开和任务失败都有恢复入口。

## 12. 安全与数据可靠性

- 使用 Argon2 保存密码摘要，永不保存或记录明文密码。
- 使用短期访问令牌和可撤销刷新令牌；客户端只在安全存储中保存令牌。
- 后端逐接口执行角色和院系数据范围校验，不能依赖前端隐藏按钮。
- 登录和敏感操作配置速率限制；生产模式要求 HTTPS 和受限跨域来源。
- 方案调整使用乐观锁，版本冲突时拒绝覆盖并要求刷新。
- 发布前执行独立全量约束复检，校验失败不得发布。
- 审计日志对普通用户只读，记录请求编号但过滤密码、令牌等敏感字段。
- SQLite 本地模式提供手动备份、恢复和导出；恢复前自动创建当前数据库快照。
- 首次启动创建初始化管理员，并强制首次登录修改临时密码。
- 演示数据通过独立命令生成，与正式数据库分离。

## 13. 异常处理

API 错误包含稳定错误码、中文消息、字段错误和请求编号。客户端将可恢复错误就地展示，将系统错误显示为简短提示并提供请求编号。

典型处理：

- Excel 格式错误：返回工作表、行号、字段和修复建议。
- 求解不可行：返回容量、组长、可用性和冲突域分析，不创建方案。
- 求解超时：若存在完整可行解则保存为草稿并标识“未证明最优”；否则保存任务诊断。
- 网络中断：客户端保留未提交表单，恢复后允许重试；幂等键避免重复写入。
- 并发修改：返回当前版本和冲突字段，不静默覆盖。
- 任务进程异常：任务标记失败并保留输入摘要，可由管理员重新执行。

## 14. 测试策略

### 14.1 单元与性质测试

- 角色权限、数据范围、导入字段校验和状态机使用单元测试。
- 约束校验器与 CP-SAT 建模使用固定案例和随机生成案例测试。
- 对多个随机种子验证：每个学生唯一分组、导师回避、资源不冲突、容量和工作量均满足。
- 已批准例外只能放宽指定对象、指定时段和指定约束。

### 14.2 集成测试

- 使用临时 SQLite 数据库覆盖登录、刷新、导入预检、确认导入、活动创建、排组、调整、审批、发布、导出和审计完整链路。
- 使用 PostgreSQL 测试容器验证迁移脚本和数据库兼容性。
- 验证失败导入整体回滚，重复请求不会产生重复任务或重复人员。

### 14.3 客户端测试

- 对 API 客户端、会话状态、角色导航和错误映射进行单元测试。
- 对三种角色执行关键流程冒烟测试。
- 在 Windows、macOS、Linux 桌面端和现代浏览器验证启动与核心页面；移动端验证只读页面。

### 14.4 性能测试

- 固定生成 500 名学生、50 名教师、20 个答辩组的合成数据集。
- 在 8 核 CPU、16 GB 内存参考环境中，60 秒内得到可行方案，峰值内存不超过 2 GB。
- 记录预检、建模、求解、复检和落库各阶段耗时，防止只看总耗时而无法定位退化。

## 15. 部署与迁移

### 15.1 本机模式

- 一个开发启动命令拉起 FastAPI 与 Flet 客户端。
- 默认使用独立 SQLite 数据文件和本地文件存储目录。
- 提供初始化管理员、生成演示数据、备份和恢复命令。

### 15.2 服务器模式

- Flet Web 和 FastAPI 作为独立服务部署，由反向代理提供 HTTPS。
- 数据库连接改为 PostgreSQL，文件使用受控服务器目录或对象存储。
- 多实例部署前将进程内任务执行器替换为 Redis 加任务队列。
- 通过数据库迁移脚本升级结构，不允许手工改生产表。

由于客户端始终调用 API、业务层不依赖 SQLite 专属语法，迁移时无需重写页面、业务规则和求解器。

### 15.3 版本管理与发布

- 子仓库默认分支为 `main`，功能开发通过短生命周期分支和 Pull Request 合入。
- 版本使用语义化标签；Classwork 的 submodule 指针只跟随经过验收的提交或版本标签。
- 本地密钥、数据库、上传文件、备份和导出结果不得进入 Git。
- public 仓库在用户明确选择开源许可证前不添加许可证文件；公开可读不自动授予再分发许可。

### 15.4 Pull Request 门禁、仓库规则与自动发布

仓库治理配置必须与代码一同接受版本控制，不只依赖 GitHub 网页中的手工设置：

- `.github/workflows/ci.yml` 在 Pull Request、`main` 推送、合并队列和手工触发时运行。它以最小只读权限执行 Ruff 格式与静态检查、严格 mypy、Python 3.12/3.14 单元与 SQLite 集成测试、PostgreSQL 集成测试、客户端测试和 Flet Web 构建冒烟；所有子任务由名称固定为 `PR Gate` 的聚合检查统一收口。
- Pull Request 标题必须使用 Conventional Commits 类型；工作流、依赖锁文件、迁移和仓库治理配置的变更也必须经过相同门禁。失败、取消或未运行的必需子任务都会使 `PR Gate` 失败，不能通过跳过工作流绕开规则。
- `.github/workflows/performance.yml` 每夜及手工运行 500 名学生的性能验收，不阻塞普通 Pull Request，但结果进入完成证据。
- `.github/rulesets/main.json` 是 `main` 分支规则的权威声明：禁止删除和强推，要求通过 Pull Request 合入，要求解决全部 review conversation，限制为 squash 或 rebase 合并，并以严格模式要求 `PR Gate` 通过。仓库只有一个 owner 时不强制他人审批，批准数为 0；owner 仍走 Pull Request 与测试门禁，紧急解锁只能通过显式停用 ruleset 并留下 GitHub 审计记录。
- `scripts/configure_github_rules.py` 通过 GitHub API 幂等创建或更新 ruleset。脚本先确认 `PR Gate` 已在远端成功运行，再激活必需检查，避免首次配置把默认分支锁死；默认 dry-run，只有显式 `--apply` 才修改远端。
- `.github/workflows/release.yml` 使用 release-please 和 Conventional Commits 维护版本 Pull Request。release PR 通过同一 `PR Gate` 并合入后，自动创建语义化标签与 GitHub Release，构建 wheel/sdist 并附加到 Release；不自动发布 PyPI、不部署服务，也不添加许可证。
- release-please 使用仓库 secret `RELEASE_PLEASE_TOKEN`，该 fine-grained token 只授予本仓库 Contents 与 Pull requests 写权限，使机器人创建的 release PR 能触发正常 CI。工作流内所有第三方 Action 固定到完整提交 SHA，并以注释记录对应版本。
- ruleset、工作流权限、触发条件、稳定检查名、发布配置和配置脚本必须有仓库级自动化测试；实际远端 ruleset 内容在最终验收时通过 GitHub API 回读并与声明文件比较。

## 16. 完成定义

首版只有同时满足以下条件才算完成：

1. 新环境按照 README 可在本机完成安装、初始化、启动和首次登录。
2. 三级角色的权限和院系数据隔离通过自动化测试。
3. 六类 Excel 模板可下载、预检、事务导入并给出逐行错误。
4. 系统能生成包含学生、教师、组长、时段和教室的完整方案。
5. 未审批硬约束在自动方案、人工调整和发布前复检中均不可被突破。
6. 例外审批具有申请、双人审批、撤销、审计和导出标识。
7. 多版本方案可比较、调整、复检、发布和导出。
8. 参考数据集达到规定的性能指标。
9. 后端、客户端和数据库迁移测试全部通过。
10. 提供 SQLite 本地运行说明以及 PostgreSQL 服务器迁移说明。
11. Pull Request 的 `PR Gate`、版本化 ruleset、夜间性能检查和自动 GitHub Release 流程均通过配置测试；远端启用 ruleset 前必须已有一次成功的 `PR Gate` 运行。
